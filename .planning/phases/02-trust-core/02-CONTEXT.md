# Phase 2: Trust Core - Context

**Gathered:** 2026-11-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Enrollment, unlock, sessions, access control, and the audit chain — server and client. After this phase only in-person-enrolled members holding their device key can see or change anything, every state change is hash-chained, and admins can invite, approve, revoke, and lock down. No incidents, alerts, chat, playbooks, or board (Phases 3–4). The audit **verifier UI** is Phase 5 (AUD-03); this phase builds the chain and a raw audit feed.

</domain>

<decisions>
## Implementation Decisions

### Roles & levels (shared/)
- **D-01:** Roles enum: `admin`, `lead`, `it`, `counsel`, `comms`, `executive`, `finance`, `hr`, `guest`, `observer`. Levels: admin=3, lead=2, it/counsel/comms/executive/finance/hr=1, guest=0, observer=0.
- **D-02:** `canInvite(inviterRole, targetRole)` in `shared/` (single source, used by server and app): admin → lead + level-1 roles + observer; lead → level-1 roles + guest; counsel → guest; everyone else → nothing. Nobody invites admin (admins only via bootstrap or two-admin promotion). Unit-tested matrix.

### Bootstrap (ENR-01)
- **D-03:** Setup code is generated by `scripts/gen-setup-code.mjs` (Node CSPRNG, 8 groups of 4 base32 chars), printed ONCE to the operator, and only its SHA-256 hex is written to root `.env` as `RP_SETUP_CODE_HASH`. Publish passes it as a declared module env var (verify exact 2.14.1 env-var mechanism in research; fallback: an owner-only `set_setup_code_hash` reducer guarded by the publisher identity recorded in `init`).
- **D-04:** `bootstrap_admin(setupCode, displayName, pubkeyHex, popSigHex)` succeeds only while fewer than 2 admins exist; the third attempt records a `security_event` and returns (no throw). Same proof-of-possession signature as redeem.

### Device key, PIN, biometrics (ENR-05, UNL-01)
- **D-05:** Device key = Ed25519 secret generated on-device with `expo-crypto` random bytes. Stored in `expo-secure-store` (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`) **encrypted** with a key derived from the PIN: PBKDF2-SHA256 via `@noble/hashes` (iterations tuned to ~200 ms on device; start 100k, constant in `shared/`), cipher `xchacha20poly1305` from `@noble/ciphers` (add dep). Wrong PIN = decrypt fails; PIN never leaves the phone.
- **D-06:** PIN: 6 digits. Unlock = `expo-local-authentication` `authenticateAsync` (falls back to device passcode; Expo Go has no Face ID on iOS — acceptable) THEN PIN entry. 5 wrong PINs → 30 s lockout (local).
- **D-07:** Duress PIN is Phase 5 (STR-04); leave a hook (optional second PIN field) but do not implement.

### Sessions & challenge (UNL-02, UNL-03, UNL-04)
- **D-08:** `request_challenge()` inserts `challenge{identity, connectionId, nonceHex (ctx.random OK — uniqueness, not secrecy), expiresAt=now+60s}`; view `my_challenge`. Client signs canonical `redphone/v1|challenge|<nonceHex>|<identityHex>` with device key; `verify_challenge(sigHex)` checks the member's stored pubkey, deletes challenge, upserts `session{identity, connectionId, createdAt, expiresAt=now+15min}`.
- **D-09:** `guard(ctx, {minRole?, fresh?})` helper: caller must be an active member, not revoked, have a live session whose `connectionId` matches `ctx.connectionId`, and lockdown must not block them. `fresh: true` (UNL-04 high-risk reducers: create_invite, revoke_member, propose/approve admin change, lockdown) additionally requires session `createdAt` within 5 min — client transparently re-challenges before high-risk actions.
- **D-10:** Client `SessionManager`: on every `onConnect` (incl. reconnect) and every 12 min, request + sign + verify challenge after unlock. Key held in memory only while foregrounded; on background > 60 s, wipe in-memory key and require unlock.
- **D-11:** Expiry cleanup by a scheduled reducer `expire_sessions` every 60 s (guarded `ctx.senderAuth.isInternal`), plus `onDisconnect` lifecycle deletes that connection's session and challenge.

### Invites (ENR-02, ENR-03, ENR-04, ENR-05)
- **D-12:** Inviter's phone generates 32-byte secret (expo-crypto), shows QR containing `redphone://invite?v=1&id=<inviteId>&s=<secretHex>&db=<dbName>`; `create_invite(role, displayName, secretHashHex)` stores only SHA-256 hex, `expiresAt=now+10min`, `createdBy`. Invite id returned via the `my_invites` view row (client matches on secretHash).
- **D-13:** `redeem_invite(inviteId, secretHex, pubkeyHex, popSigHex)`: hash check (timing-safe compare), not expired, not used, `canInvite(inviter.role, invite.role)` re-checked, PoP signature over `redphone/v1|redeem|<inviteId>|<identityHex>|<pubkeyHex>`; atomically marks used and inserts member `{identity, displayName (from invite), role (from invite), pubkeyHex, fingerprint, invitedBy, status:'active', createdAt}`. Any failure → security_event + return.
- **D-14:** Key fingerprint = first 16 hex of SHA-256(pubkey bytes), displayed as 4 groups of 4 (`ABCD EF01 2345 6789`), in `shared/`.

### Admin changes, revoke, lockdown (ENR-06..09)
- **D-15:** Generic `admin_proposal{id, kind: promote|demote|revoke_admin, target, proposedBy, createdAt, status}` + `admin_approval{proposalId, approver}`. Executes when 2 distinct admin approvals exist, neither approver is the target (proposer counts as first approval). `.isEqual()` for all identity comparisons.
- **D-16:** `revoke_member(target)` (admin only; non-admin targets): sets status `revoked` on target and every descendant in the invite tree (iterative walk over `member.invitedBy` btree index), deletes their sessions/challenges/unused invites. Revoking an admin must go through D-15.
- **D-17:** `config` singleton row: `lockdown: bool`, `setupCodeHash`, `adminCount`. `set_lockdown(on)` admin-only, fresh session; when on, `guard` rejects all non-admins and their sessions are deleted.

### Audit chain (AUD-01, AUD-02)
- **D-18:** `audit_log{seq u64 PK, at Timestamp, actor Identity, action string, dataHash hex, prevHash hex, hash hex}` + `audit_head` singleton `{seq, hash}`. `appendAudit(ctx, action, fields: Record<string,string>)`: canonical data = pipe-joined `key=value` sorted by key (bigints as decimal, bytes as lowercase hex); `hash = sha256("redphone/v1|audit|" + seq + "|" + atMicros + "|" + actorHex + "|" + action + "|" + dataHash + "|" + prevHash)`. Genesis prevHash = 64 zeros. Canonicalization lives in `shared/` with test vectors so the Phase 5 client verifier matches byte-for-byte.
- **D-19:** `security_event` failures also go through `appendAudit` (action `security.<reason>`), so failed checks are chained (AUD-02). Reducers record and **return**; they only throw for programmer errors.

### Visibility (AUD-05)
- **D-20:** All tables private. Views (public, indexed lookups only): `my_member`, `roster` (all active members: displayName, role, fingerprint — only if caller is active+session), `my_challenge`, `my_invites` (inviter's own; admins see all pending via index on status), `admin_proposals` (admins only), `audit_feed` (admins only; last N via seq — research how to page without `.iter()`), `app_config` (lockdown flag only). Anonymous / token-only callers get `[]` everywhere.

### Client UX (UI)
- **D-21:** Expo Router gates: `(gate)/welcome` (scan invite or first-time setup) → `enroll/pin` → `(app)` tabs after unlock; `unlock` screen when key locked. Screens: Welcome, Scan Invite (expo-camera, `useRef` scan lock), Set PIN, Unlock, Home (my role + fingerprint + roster), Invite (role picker → full-screen QR + countdown), Members (revoke, propose admin change, approve), Lockdown toggle (admins), Audit feed (admins, raw list). Big buttons, group-text feel, high contrast; UI-SPEC from gsd-ui-phase governs visuals.
- **D-22:** Phase 1 spike screen moves to a dev-only route `/dev/spike`; spike tables stay in the module (inert) until the Phase 5 schema freeze.
